## 1. ПАСПОРТ ПРОЕКТА И ОБЩАЯ ИНФОРМАЦИЯ

*   **Тема ВКР:** Разработка интеллектуального сервиса для подготовки к путешествиям.
*   **Название сервиса:** Luggify.
*   **Направление подготовки:** 09.03.01 «Информатика и вычислительная техника» (МАИ, Кафедра 316).
*   **Актуальность:** Планирование поездки — сложный многосоставной процесс, требующий учета множества динамических факторов: погодных условий, длительности, типа транспорта, визовых и технических особенностей страны назначения, а также координации списков вещей и совместного багажа. Существующие аналоги (PackPoint, Packr, TripIt) имеют существенные ограничения: отсутствие полноценной веб-версии или Telegram-интеграции, платные подписки на базовые функции, отсутствие совместного редактирования багажа и примитивные алгоритмы без использования современных LLM.
*   **Объект исследования:** Процесс организации, планирования и информационного сопровождения туристических и деловых поездок.
*   **Предмет исследования:** Методы, алгоритмы и программные средства интеллектуального формирования чеклистов, распределения багажа, планирования маршрутов и кроссплатформенного взаимодействия пользователей.
*   **Цель работы:** Разработка клиент-серверного интеллектуального сервиса подготовки к путешествиям, обеспечивающего автоматизированное формирование списков вещей на основе метеорологических данных, кроссплатформенный доступ (Web SPA, Telegram Bot, Telegram Mini App) и возможности совместного планирования.
*   **Основные задачи:**
    1. Системный анализ предметной области и недостатков существующих решений (PackPoint, Packr, TripIt, AnyList).
    2. Обоснование выбора клиент-серверной архитектуры и технологического стека (React, FastAPI, PostgreSQL, aiogram, Gemini API).
    3. Проектирование реляционной модели данных (3NF) с использованием JSONB для хранения погодных сводок и динамических списков вещей.
    4. Проектирование и реализация REST API для синхронизации клиентских приложений и управления сущностями поездки, багажа и маршрута.
    5. Разработка подсистемы ИИ на базе Gemini API для интеллектуальных консультаций, формирования рекомендаций и составления плана дня.
    6. Разработка детерминированного модуля распознавания намерений (intents) для быстрой и экономной обработки команд пользователя на естественном языке.
    7. Создание клиентского веб-приложения (React SPA), Telegram-бота и Telegram Mini App (TMA).
    8. Реализация механизмов локального сохранения состояния (оффлайн-режим) и фоновой синхронизации.
    9. Тестирование, контейнеризация (Docker Compose) и формулирование перспектив развития (включая разработку Android-приложения).

## 2. АРХИТЕКТУРА СИСТЕМЫ И ВЗАИМОДЕЙСТВИЕ КОМПОНЕНТОВ

Система построена по **клиент-серверной архитектуре** с единым бэкендом в качестве общей точки истины.

┌────────────────────────────────────────────────────────────────────────┐

### Детальное описание компонентов:
1. **FastAPI Backend (`server/`):** Ядро системы, объединяющее бизнес-логику, авторизацию, ИИ-движок и управление базой данных. Обрабатывает запросы от веб-клиента и Telegram Mini App, а также содержит встроенного или отдельно запускаемого Telegram-бота.
2. **PostgreSQL Database:** Основное хранилище данных, обеспечивающее строгую реляционную целостность для связей пользователей и гибкость JSONB для динамических структур (погода, списки).
3. **Web SPA Client (`client/src/`):** Полнофункциональное клиентское приложение на React 18, в котором пользователь управляет поездками, багажом, профилем и общается с ИИ-виджетом.
4. **Telegram Mini App (`client/src/tma/`):** Специализированный модуль клиентского приложения, адаптированный под WebView внутри Telegram. Обращается к бэкенду, используя валидацию `initData`.
5. **Telegram Bot (`server/telegram_bot/`):** Модуль на базе фреймворка `aiogram`, обеспечивающий текстовый и кнопочный интерфейс в мессенджере. Позволяет выполнять команды над чеклистом без открытия браузера.
6. **AI Subsystem (`server/ai_service.py`, `checklist_ai.py`, `assistant_intents.py`):** Комбинированный ИИ-модуль, включающий интеграцию с LLM Gemini для сложных задач и локальный детерминированный парсер для быстрых команд.

## 3. ТЕХНОЛОГИЧЕСКИЙ СТЕК И ОБОСНОВАНИЕ ВЫБОРА

### 3.1 Серверная часть (Backend)
*   **Python 3.11+:** Основной язык серверной разработки. Выбран за лидирующие позиции в сфере ИИ, высокую скорость прототипирования и мощную асинхронную экосистему.
*   **FastAPI:** Современный асинхронный веб-фреймворк. Обоснование выбора: превосходит Django и Flask по скорости работы (благодаря архитектуре ASGI и библиотеке Starlette/Pydantic), обеспечивает автоматическую генерацию спецификации OpenAPI (Swagger) и строгую валидацию типов.
*   **Uvicorn:** Высокопроизводительный ASGI-сервер на базе `uvloop`.
*   **SQLAlchemy 2.0:** Индустриальный стандарт ORM в Python. Используется в связке с асинхронным драйвером `asyncpg` для неблокирующего доступа к PostgreSQL.
*   **Pydantic 2.0:** Обеспечивает жесткую валидацию и сериализацию структур данных (схем запросов и ответов) на основе аннотаций типов Python.
*   **Alembic:** Инструмент для версионирования схемы БД и автоматического создания миграций.
*   **python-jose, passlib (bcrypt):** Обеспечивают криптографическую защиту паролей и управление сессиями через JWT (JSON Web Tokens).

### 3.2 Клиентская часть (Web Frontend & TMA)
*   **React 18:** Библиотека для создания декларативных пользовательских интерфейсов. Обоснование выбора: компонентная архитектура, виртуальный DOM и огромная экосистема делают React идеальным выбором для сложных SPA.
*   **Vite:** Современный сборщик фронтенда, обеспечивающий мгновенный запуск сервера разработки (HMR) и высокооптимизированную сборку продакшн-бандла (превосходит Webpack по скорости в 10–20 раз).
*   **React Router DOM:** Обеспечивает навигацию и маршрутизацию между страницами (поездка, профили, авторизация, TMA) без перезагрузки страницы.
*   **Vanilla CSS:** Использование чистого CSS (с переменными, Flexbox и Grid) для точной и легковесной стилизации интерфейса под десктопные, мобильные экраны и Telegram Mini App без перегрузки бандла сторонними UI-библиотеками.
*   **react-datepicker, react-select:** Проверенные компоненты для удобного выбора диапазонов дат и фильтрации списков городов.

### 3.3 Telegram-интеграция
*   **aiogram 3.x:** Современный асинхронный фреймворк для Telegram-ботов на Python. Обоснование выбора: полная поддержка актуального Telegram Bot API 7.x, удобная система роутеров, фильтров и промежуточных обработчиков (middlewares), высокая производительность.
*   **Telegram Web Apps API:** Платформа для интеграции веб-приложений внутрь мессенджера (TMA).

### 3.4 База данных и инфраструктура
*   **PostgreSQL 16:** Мощная объектно-реляционная СУБД. Обоснование выбора: полная поддержка ACID, высокая надежность и наличие полей `JSONB`, позволяющих эффективно индексировать и хранить сложные погодные сводки и динамические списки вещей без создания избыточных таблиц.
*   **Docker и Docker Compose:** Инструменты контейнеризации. Обеспечивают полную изоляцию окружения (БД, бэкенд, фронтенд, бот), стандартизацию развертывания на любом сервере и удобство локальной разработки.

### 3.5 Внешние сервисы и ИИ
*   **Gemini API (Google AI):** Передовая LLM (Gemini 1.5 Pro / Flash). Выбрана за огромное контекстное окно, высокую скорость генерации, поддержку структурированного вывода (JSON) и отличное понимание естественного языка в задачах travel-консалтинга.
*   **Open-Meteo API:** Бесплатный метеорологический сервис, предоставляющий архивные данные и точные прогнозы на 16 дней без необходимости сложных API-ключей.
*   **Nominatim (OpenStreetMap):** Сервис геокодирования для поиска координат и нормализации названий городов.
*   **Google Places API (через RapidAPI):** Используется для поиска достопримечательностей, отелей и заведений.

## 4. СТРУКТУРА БАЗЫ ДАННЫХ И РЕЛЯЦИОННАЯ МОДЕЛЬ (ORM)

База данных спроектирована в третьей нормальной форме (3NF) с точечным использованием JSONB для неструктурированных или часто меняющихся массивов (погода, списки). Реализована в файле `server/models.py`.

```
┌─────────────────┐       ┌─────────────────┐       ┌─────────────────┐
│     USERS       │1     M│   CHECKLISTS    │1     M│    BAGGAGE      │
│(Пользователи)   ├───────┤   (Поездки)     ├───────┤    (Багаж)      │
│- id (UUID)      │       │- slug (PK)      │       │- id (PK)        │
│- email          │       │- title          │       │- checklist_slug │
│- password_hash  │       │- city / dates   │       │- name           │
│- tg_id          │       │- items (JSONB)  │       │- is_main        │
└────────┬────────┘       └────────┬────────┘       └────────┬────────┘
         │1                        │1                        │1
         │M                        │M                        │M
┌────────▼────────┐       ┌────────▼────────┐       ┌────────▼────────┐
│  USER_PROFILES  │       │ TRIP_PARTICIPANTS│      │ BAGGAGE_SECTIONS│
│(Профили/Соц)    │       │(Участники)      │       │(Секции/Вещи)    │
│- user_id (PK)   │       │- checklist_slug │       │- baggage_id     │
│- is_public      │       │- user_id / role │       │- name           │
└─────────────────┘       └─────────────────┘       └─────────────────┘
```

### Детальное описание таблиц (`server/models.py`):
1.  **`users` (Пользователи):**
    *   `id` (UUID, PK, default=uuid4): Уникальный идентификатор.
    *   `email` (String, Unique, Index): Электронная почта.
    *   `password_hash` (String): Хэш пароля (bcrypt).
    *   `tg_id` (String, Unique, Nullable, Index): Telegram ID для связывания аккаунта.
    *   `created_at`, `updated_at` (DateTime).

2.  **`checklists` (Поездки / Чеклисты — центральная сущность):**
    *   `slug` (String, PK, Index): Уникальный строковый идентификатор (например, `анталия-2026-abc123`).
    *   `owner_id` (UUID, FK -> users.id, Index): Создатель поездки.
    *   `title` (String): Название поездки.
    *   `city` (String): Место назначения.
    *   `start_date`, `end_date` (Date): Даты поездки.
    *   `transport` (String): Тип транспорта (самолет, поезд, авто).
    *   `items` (JSONB): Исходный сгенерированный список вещей (массив строк).
    *   `checked_items` (JSONB): Список собранных вещей.
    *   `removed_items` (JSONB): Список удаленных пользователем вещей.
    *   `added_items` (JSONB): Список добавленных вручную вещей.
    *   `weather_data` (JSONB): Кеш прогноза погоды (температуры, осадки).
    *   `is_public` (Boolean, default=False): Флаг публичного доступа.
    *   `created_at`, `updated_at` (DateTime).

3.  **`trip_participants` (Участники совместной поездки):**
    *   `id` (UUID, PK).
    *   `checklist_slug` (String, FK -> checklists.slug, Index).
    *   `user_id` (UUID, FK -> users.id, Nullable): Привязанный аккаунт (если есть).
    *   `role` (String): Роль участника (`owner`, `editor`, `viewer`, `child`).
    *   `name` (String): Отображаемое имя (важно для детей/гостей без аккаунта).

4.  **`baggage` (Структура багажа):**
    *   `id` (UUID, PK).
    *   `checklist_slug` (String, FK -> checklists.slug, Index).
    *   `name` (String): Название («Большой чемодан», «Ручная кладь»).
    *   `is_main` (Boolean, default=False): Флаг основного чемодана.
    *   `owner_participant_id` (UUID, FK -> trip_participants.id, Nullable): Владелец чемодана.

5.  **`baggage_sections` (Секции и категории внутри багажа):**
    *   `id` (UUID, PK).
    *   `baggage_id` (UUID, FK -> baggage.id, Index).
    *   `name` (String): Название секции («Одежда», «Техника», «Документы»).
    *   `items` (JSONB): Массив строк (вещи, лежащие в этой секции).

6.  **`user_profiles` (Публичные профили пользователей):**
    *   `user_id` (UUID, PK, FK -> users.id).
    *   `username` (String, Unique, Index).
    *   `bio`, `avatar_url` (String, Nullable).
    *   `is_public` (Boolean, default=False).

7.  **`notifications`, `trip_routes`, `trip_invitations`, `reviews`:** Вспомогательные таблицы для хранения уведомлений, точек сложного маршрута, инвайтов и отзывов.

## 5. ОПИСАНИЕ КЛЮЧЕВЫХ REST API ЭНДПОИНТОВ

API бэкенда спроектирован по стандартам RESTful, описан схемами Pydantic в `server/schemas.py` и реализован в `server/main.py`.

### 5.1 Авторизация и связывание (`/auth`, `/tg`)
*   `POST /auth/register`: Регистрация пользователя. Принимает `UserCreate` (`email`, `password`). Хэширует пароль и сохраняет в БД.
*   `POST /auth/login`: Вход пользователя. Принимает `OAuth2PasswordRequestForm`. Возвращает JWT токен: `{ "access_token": "eyJ...", "token_type": "bearer" }`.
*   `GET /auth/me`: Получение данных текущего пользователя (по JWT из заголовка `Authorization`).
*   `POST /tg/auth`: Авторизация через Telegram Mini App. Принимает `initData`, проверяет HMAC-SHA256 подпись с помощью `TELEGRAM_BOT_TOKEN`, находит или создает пользователя по `tg_id`.
*   `POST /tg/link`: Связывание Telegram-аккаунта с существующим веб-аккаунтом по email и паролю.

### 5.2 Управление поездками и генерация (`/checklists`)
*   `POST /generate-packing-list`: Главный эндпоинт интеллектуальной генерации. Принимает `PackingRequest`:
    ```json
    { "city": "Москва, Россия", "start_date": "2026-06-01", "end_date": "2026-06-10", "transport": "plane" }
    ```
    Логика работы (реализована в `server/packing_advisor.py`, `packing_logic.py`): обращается к Open-Meteo, получает погоду, формирует базовый список вещей, создает запись в таблице `checklists`, создает дефолтный багаж (`baggage`) и секции (`baggage_sections`). Возвращает полный объект `Checklist`.
*   `GET /checklist/{slug}`: Получение полной агрегированной информации о поездке (погода, участники, багаж, списки вещей).
*   `PATCH /checklist/{slug}/state`: Синхронизация состояния чеклиста. Принимает `ChecklistStateUpdate`:
    ```json
    { "checked_items": ["Паспорт"], "removed_items": ["Фен"], "added_items": ["Очки"] }
    ```
    Обновляет JSONB поля в БД.
*   `POST /checklist/{slug}/invitations`: Создание ссылки-приглашения для совместного доступа.

### 5.3 Управление багажом (`/baggage`)
*   `POST /checklist/{slug}/baggage`: Создание новой единицы багажа (принимает `BaggageCreate`).
*   `PATCH /baggage/{baggage_id}/items`: Перемещение вещей между секциями и чемоданами.

### 5.4 AI-Ассистент и команды (`/ai`)
*   `POST /ai/ask`: Отправка вопроса в контексте поездки. Принимает `slug` и `question`. Обращается к `ai_service.py`.
*   `POST /ai/command`: Обработка быстрой команды над чеклистом. Принимает `slug` и `command` («добавь аптечку»). Обращается к `assistant_intents.py`.

### 6.1 Генеративный AI-ассистент (Gemini API)
Реализован в `server/checklist_ai.py` и `ai_service.py`. Отвечает за решение сложных, неструктурированных задач: консультации по правилам авиакомпаний, подбор гардероба под специфический климат, формирование packing-рекомендаций и автоматическое составление плана дня (`assistant_plan_service.py`).
*   **Механизм работы:** При обращении пользователя модуль агрегирует полный контекст поездки (через `server/trip_context.py`), включающий: город, даты, погодную сводку (мин/макс температуры, осадки), текущий список вещей (собранные/несобранные), структуру багажа и состав участников (включая детей).
*   **Инженерия промптов (Prompt Engineering):** Сервер формирует обогащенный системный промпт:
    ```text
    Ты — профессиональный travel-ассистент Luggify. Контекст поездки: Город {city}, даты {dates}, погода: {weather_summary}. В поездке участвуют: {participants}. Текущий багаж: {baggage_list}. Отвечай на вопрос пользователя кратко, предлагай конкретные практические советы по сбору вещей и организации поездки.
    ```
    Запрос отправляется в Google Gemini API. Полученный ответ (включая структурированные JSON-рекомендации) возвращается клиенту.

### 6.2 Детерминированный модуль распознавания намерений
Реализован в `server/assistant_intents.py`. Разработан для решения проблемы высокой задержки (latency) и финансовых затрат при выполнении тривиальных команд через LLM.
*   **Принцип работы:** Запросы вида `«добавь powerbank»`, `«удали фен»`, `«отметь паспорт»` перехватываются локальным скриптованным модулем.
*   **Алгоритм:** Модуль использует регулярные выражения и эвристический анализ для распознавания намерения (intent: `ADD`, `REMOVE`, `CHECK`, `UNCHECK`) и извлечения сущностей (entities: названия вещей).
*   **Преимущества комбинированного подхода:**
    1. **Скорость:** Простые команды выполняются за 10–20 мс (вместо 2–4 секунд ожидания от Gemini).
    2. **Надежность:** Исключаются галлюцинации ИИ при выполнении точных операций над БД.
    3. **Экономия:** Снижается количество платных обращений к внешнему API Gemini.

## 7. ТЕЛЕГРАМ-БОТ И TELEGRAM MINI APP (TMA)

Интеграция с Telegram реализована для обеспечения удобного доступа к сервису со смартфона без необходимости открывать браузер.

### 7.1 Telegram Mini App (`client/src/tma/TmaApp.jsx`)
*   **Концепция:** Полноценное React-приложение, открывающееся во встроенном браузере Telegram (Webview) по кнопке в боте.
*   **Техническая реализация:** TMA встроен в основное React-приложение по маршруту `/tma`. При открытии приложение получает строку `window.Telegram.WebApp.initData`, отправляет ее на бэкенд (`/tg/auth`), где происходит проверка HMAC-SHA256 подписи.
*   **Сценарий:** Пользователь открывает TMA, видит свои поездки в мобильном интерфейсе (`TmaApp.css`), отмечает вещи в чеклисте одним тапом. Все изменения отправляются на FastAPI бэкенд.

### 7.2 Telegram-бот (`server/telegram_bot/`)
*   **Архитектура:** Автономный модуль на базе асинхронного фреймворка `aiogram 3.x`. Включает файлы `main.py` (запуск), `services.py` (бизнес-логика бота), `keyboards.py` (клавиатуры) и `config.py`.
*   **Связывание аккаунтов (Account Linking):** При отправке команды `/trip` или `/start` бот ищет пользователя в БД по `tg_id`. Если аккаунт не найден, бот предлагает авторизоваться через TMA или привязать существующий веб-аккаунт по email (`/telegram_link.py`).
*   **Управление чеклистом через чат:** Пользователь может отправить боту текстовое сообщение: `«в поездке в Стамбул удали фен и добавь аптечку»`. Бот определяет активную поездку, запрашивает подтверждение (кнопки `Да / Нет` в `keyboards.py` для защиты от случайного удаления) и выполняет операцию через `services.py`.

## 8. ОФФЛАЙН-РЕЖИМ И СИНХРОНИЗАЦИЯ (КЛИЕНТСКАЯ ЧАСТЬ)

Для обеспечения бесперебойной работы веб-клиента в условиях нестабильного мобильного интернета (в аэропорту, поезде) реализована подсистема оффлайн-хранения в файлах `client/src/offlineChecklist.js` и `packingState.js`.

```
┌────────────────────────────────────────────────────────────────────────┐
│                        ПОЛЬЗОВАТЕЛЬСКОЕ ДЕЙСТВИЕ                       │
│                       (Отметка вещи в чеклисте)                        │
└────────────────────────────────────┬───────────────────────────────────┘
                                     │
                                     ▼
┌────────────────────────────────────────────────────────────────────────┐
│         МГНОВЕННОЕ ОБНОВЛЕНИЕ ЛОКАЛЬНОГО СОСТОЯНИЯ (React State)       │
└────────────────────────────────────┬───────────────────────────────────┘
                                     │
                                     ▼
┌────────────────────────────────────────────────────────────────────────┐
│           СОХРАНЕНИЕ В ЛОКАЛЬНОЕ ХРАНИЛИЩЕ (localStorage)              │
│               (Снимок данных через offlineChecklist.js)                │
└────────────────────────────────────┬───────────────────────────────────┘
                                     │
                                     ▼
┌────────────────────────────────────────────────────────────────────────┐
│               ПРОВЕРКА НАЛИЧИЯ ИНТЕРНЕТА (navigator.onLine)            │
└──────────────┬──────────────────────────────────────────┬──────────────┘
               │ ОНЛАЙН                                   │ ОФФЛАЙН
               ▼                                          ▼
┌──────────────────────────────┐          ┌──────────────────────────────┐
│  Отправка PATCH-запроса на   │          │  Пометка данных флагом       │
│  FastAPI Backend             │          │  isDirty = true              │
│                              │          │                              │
│  (Синхронизация успешна)     │          │  (Ожидание появления сети)   │
└──────────────────────────────┘          └──────────────┬───────────────┘
                                                         │
                                                         ▼
                                          ┌──────────────────────────────┐
                                          │ При восстановлении сети:     │
                                          │ Фоновая отправка             │
                                          │ накопившихся изменений на    │
                                          │ сервер                       │
                                          └──────────────────────────────┘
```

### Механизм работы (`client/src/offlineChecklist.js`):
1.  **Локальный кэш:** При открытии поездки клиент сохраняет полную копию объекта `Checklist` в `localStorage` браузера.
2.  **Оптимистичный UI (Optimistic UI):** При клике на чекбокс вещи интерфейс обновляется мгновенно в React State, не дожидаясь ответа от сервера.
3.  **Оффлайн-очередь:** Если интернет пропадает (`navigator.onLine === false`), изменения (отмеченные/добавленные/удаленные вещи) сохраняются локально с флагом `isDirty = true`. В UI появляется индикатор «Работа в оффлайн-режиме».
4.  **Фоновая синхронизация:** При восстановлении сетевого соединения срабатывает обработчик события `window.addEventListener('online', ...)`. Клиент в фоновом режиме отправляет накопившийся пакет изменений (`PATCH /checklist/{slug}/state`) на сервер.
5.  **Разрешение конфликтов:** При совместном доступе приоритет отдается серверной метке времени (`updated_at`) или применяется стратегия слияния списков (union) для предотвращения потери данных.

## 11. ПЕРСПЕКТИВЫ ДАЛЬНЕЙШЕГО РАЗВИТИЯ (ДЛЯ ГЛАВЫ 4 / ЗАКЛЮЧЕНИЯ)

В рамках исследования сформирован четкий план дальнейшего развития сервиса Luggify, в котором приоритетным направлением является **разработка нативного мобильного приложения для ОС Android**.

### План реализации Android-приложения (Архитектурное видение):
1. **Технологический стек:** Приложение будет разрабатываться на языке **Kotlin** с использованием современного декларативного UI-фреймворка **Jetpack Compose** (соответствует концепции React SPA на веб-клиенте).
2. **Архитектурный паттерн:** Планируется использование паттерна **MVVM (Model-View-ViewModel)** в связке с чистой архитектурой (Clean Architecture) и репозиториями (`LuggifyRepository`), что обеспечит изоляцию UI от сетевой логики.
3. **Сетевое взаимодействие:** Для связи с существующим FastAPI бэкендом будет использоваться библиотека **Retrofit** в связке с **Kotlin Coroutines** (`suspend` функции), что позволит бесшовно вызывать существующие REST API эндпоинты (`/auth`, `/checklists`, `/baggage`).
4. **Локальное хранение и оффлайн-режим:** Вместо устаревшего `SharedPreferences` планируется внедрение **Jetpack DataStore** для асинхронного сохранения настроек (выбранный город, даты, вещи по умолчанию) и кэширования чеклистов с помощью базы данных **Room** (для полноценной работы в оффлайне).
5. **Управление состоянием:** В качестве реактивного источника истины для UI будет применяться **StateFlow** (`MutableStateFlow(UiState)`), что обеспечит автоматическую перерисовку экранов при изменении данных о багаже или чеклисте.
